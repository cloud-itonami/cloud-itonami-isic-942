What this store can and cannot tell you

Measured at render time by scanning the real records this run produced — not asserted in the source. If the store is ever changed, these paragraphs change with it.

Approver attribution. Scanned all 5 committed record(s); their complete key set is member-id, operation, status, timestamp. None of the 17 approver-identity keys this renderer looks for is present, and none is present on the decision results either. This is not the store dropping an approver it was given: tradeunionorg.operation/decide returns :APPROVE / :HOLD / :ESCALATE and there is no human-approval step anywhere in this stack that would produce an identity to record. So the honest reading of a committed row below is "the governor passed it and the actor committed it", not "a named person approved it". Escalated rows say a human must review, but nothing records who did.
Which layer drops the approver. "No approver" above could mean nobody approved, or it could mean someone did and the write path discarded them. The scan alone cannot tell those apart, because nothing in this stack supplies an approver to begin with. So this renderer supplies one: it puts approver on a proposal and on a raw ledger record, runs both through the real code against throwaway stores, and reports what survived. The store is not the culprit. Handed a record that already carried approver, MemStore/append-ledger stored it unchanged — it keeps whatever it is given and destructures nothing. But putting approver on a proposal and running the real flow (which returned APPROVE) produced a ledger record whose complete key set is member-id, operation, status, timestamp: the approver is gone. tradeunionorg.operation/commit does not forward the decision or the proposal — it builds a fresh four-key record from scratch, so every field not named in it is dropped at that line. That matters for anyone fixing this: adding a human-approval step upstream would not put an approver in the ledger on its own, because commit would still discard it.
The ledger only records what succeeded. This run produced 14 dispositions (committed 5, escalated 2, governor-hold 6, intake-rejected 1), but the append-only ledger holds 5 record(s) (APPROVE 5). tradeunionorg.operation/flow calls commit only on the :APPROVE branch, so every HARD hold and every escalation above leaves no trace in the store at all. The refusals on this page exist because the renderer captured the return values; an operator reading the ledger alone could not reconstruct them. Recording refusals is a governance change with its own contract, so it is disclosed here rather than patched by this renderer.
Some governor findings never reach the decision. In 1 of the 14 scenarios the flow reached the governor, the governor returned violations, and the decision did not carry them forward. tradeunionorg.operation/decide tests for :flag-safety-concern before it tests :passes?, so a safety report escalates even when the member who filed it fails HARD check #1. Escalating a safety report regardless of the reporter's standing is defensible; silently discarding the finding is the part worth knowing — the escalation handed to the human reviewer carries no :violations key at all, so nothing tells the reviewer that the reporter failed verification. Affected: Same safety report, filed by an unregistered member (member-unverified).
Malformed proposals are refused before the governor is consulted. 1 scenario(s) were rejected by tradeunionorg.operation/intake, which returns an :ERROR that makes flow return immediately — the governor and decide never ran for them. The violations shown in their row come from a separate governor/govern call this renderer makes for comparison, and are labelled in the table as such. They are NOT counted as HARD holds anywhere on this page, because the actor never made that finding. Affected: Supply request submitted with no :effect field.
